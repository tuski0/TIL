## 1. 예매 관리자 기능: 별도 라우터 없이 역할로 관리자 판단하기

### 막힌 점, 고민

- 관리자 기능을 `/admin` 라우터로 따로 만들어야 할지, 기존 예매 라우터에서 처리해야 할지 헷갈렸음
- 같은 엔드포인트를 일반 사용자와 관리자가 같이 쓰면 권한 구분을 어디서 해야 할지 몰랐음
- 권한이 없을 때 404를 줘야 할지 403을 줘야 할지 기준이 없었음

### 무엇을 어떻게 했나

- users 도메인의 `is_owner or is_admin` 방식을 참고해서 **기존 예매 라우터에서 역할(`UserRole`)로 판단**하기로 함
- 엔드포인트별 동작을 표로 정리함

| 엔드포인트              | 일반 사용자                   | 관리자                      |
| ----------------------- | ----------------------------- | --------------------------- |
| 단건 조회               | 내 예매만 (남의 예매면 404)   | 모든 예매                   |
| 예매 취소               | 내 예매만, 시작 24시간 전까지 | 모든 예매, 공연 시작 전까지 |
| 축제별 예매 목록 (신규) | 403                           | 조회 가능                   |

- 확인 위치를 둘로 나눔
  - "본인 또는 관리자" (단건 조회·취소) → 서비스에서 판단
  - "관리자 전용" (목록) → 라우터에서 바로 403

### 어떻게 풀었나

- 404와 403은 **무엇을 숨기고 싶은지**로 구분함
  - 남의 예매 조회 → 404 : 그 예매가 존재한다는 사실 자체를 숨김
  - 관리자 전용 목록 → 403 : 기능은 있지만 권한이 없음을 알림
- 관리자용 기능을 따로 만들지 않아도 되어서 엔드포인트와 코드 중복이 줄어듦
- 로그인 의존성(#116 `get_current_user`)은 `user_id`만 돌려줘서 role을 알 수 없음 → 관리자 검사는 users의 `verify_admin`을 사용하기로 함

## 2. 축제·회차 취소 시 예매 일괄 취소

### 막힌 점, 고민

- 축제가 취소되면 그 축제의 예매를 어떻게 처리해야 할지 몰랐음
- 처음에는 기존 `cancel_reservation`을 반복문으로 부르면 된다고 생각했음
- 축제 서비스가 예매 서비스를 부르면 생기는 문제를 몰랐음
- 축제 취소는 성공하고 예매 취소는 실패하면 데이터가 어긋나지 않을지 걱정됐음

### 무엇을 어떻게 했나

- 세 가지 방법(일괄 취소 / 상태 유지 + 환불만 / 사용자 취소 허용)을 비교하고 **일괄 취소**로 정함
- 기존 `cancel_reservation`을 재사용하면 안 되는 이유를 정리함

| 항목           | 일반 취소     | 일괄 취소                                         |
| -------------- | ------------- | ------------------------------------------------- |
| 본인 확인      | 필요          | 불필요 (시스템이 하는 취소)                       |
| 취소 마감 검사 | 함            | 건너뜀 (축제 쪽 사정)                             |
| 잔여 수량 복구 | 함            | 취소된 회차는 건너뜀 (`increase_remaining`이 409) |
| 대상           | 엔티티가 판단 | PENDING, CONFIRMED만 미리 골라냄                  |

- 이미 CANCELED/EXPIRED인 예매에 `cancel()`을 부르면 409가 나서, 예매 하나 때문에 전체가 실패할 수 있음 → 대상 상태를 처음부터 골라냄
- 양일권은 **부분 취소 없음**을 유지함 → 토요일 회차만 취소돼도 양일권 예매 전체 취소

### 어떻게 풀었나

- 순환 import
  - 지금은 `예매 → 축제` 한 방향으로만 참조함
  - 축제 서비스가 예매 서비스를 import하면 서로 참조하게 되어 서버 시작 시 `ImportError`가 날 수 있음
  - 라우터·wiring에서 두 서비스를 차례로 부르거나 주입받는 방식으로 피할 수 있음 → 축제 담당과 협의 안건
- 트랜잭션
  - 저장소 구현체를 찾아보니 모두 `flush()`만 하고, `commit()`은 `shared/core/database.py` 한 곳에서만 함
  - 요청 하나가 세션 하나를 쓰고 마지막에 한 번만 commit하므로 **중간에 실패하면 전부 rollback**됨
- 남은 문제
  - 토요일 회차 취소로 양일권이 취소되면 그 예매가 잡고 있던 **일요일 자리**가 비게 됨
  - 살아 있는 회차만 수량을 복구하는 분기가 필요함 → 협의 안건으로 남김

## 3. 관리자 예매 목록 API URL: 경로 방식 vs 쿼리 방식

### 막힌 점, 고민

- 축제별 목록 URL을 `/festivals/{id}/...`(경로)로 할지 `?festival_id=`(쿼리)로 할지 기준이 없었음
- 튜터 repo를 따라 이슈 #117에 `GET /v1/festivals/{festival_id}/reservations`로 적었는데, URL이 `/festivals`로 시작하니 축제 담당이 해야 하는 일인지 헷갈렸음
- 예매 라우터의 prefix가 `/v1/reservations`라서 그냥 추가하면 경로가 `/v1/reservations/festivals/...`가 되는 문제도 있었음

### 무엇을 어떻게 했나

- 두 방식의 차이를 정리함

| 방식 | 예시                           | 의미                                            |
| ---- | ------------------------------ | ----------------------------------------------- |
| 경로 | `/festivals/{id}/performances` | 부모에 속한 자식이라는 소속 관계를 URL로 표현   |
| 쿼리 | `/performances?festival_id=1`  | 전체 목록에서 조건으로 걸러냄, 필터 추가가 쉬움 |

- 튜터 repo의 규칙을 확인함
  - 부모에 속한 목록·생성 → `/boards/{board_id}/posts`
  - 자식 하나 조회·수정·삭제 → `/posts/{post_id}`
- 이 API가 어느 도메인의 일인지 **다루는 데이터** 기준으로 따져 봄
  - 조회하는 데이터는 예매 테이블임
  - 저장소 메서드(`find_festival_reservation`, `count_festival_reservation`)와 응답 스키마(`ReservationResponse`)도 전부 예매 쪽에 있음
- 축제 쪽에 맡길 때 생기는 일을 정리함

| 구분            | 축제 담당에게 요청                        | 예매에서 직접                     |
| --------------- | ----------------------------------------- | --------------------------------- |
| 내가 할 일      | 서비스 메서드 + 스키마                    | 서비스 메서드 + 스키마 + 라우터   |
| 축제 담당 할 일 | 라우터 추가 + 예매 서비스 연결            | 없음                              |
| 의존 방향       | festivals → reservations 의존이 새로 생김 | 그대로 (reservations → festivals) |
| 일정            | 축제 담당 일정에 묶임                     | 혼자 진행 가능                    |

- 축제 쪽에 맡겨도 로직은 결국 예매 쪽에 있어야 해서, 요청할 수 있는 건 사실상 라우터 등록뿐이었음
- 경로 방식을 예매 쪽에 두는 방법도 찾아봄
  - 예매 라우터 파일에 prefix가 `/v1/festivals`인 `APIRouter`를 하나 더 만들기
  - prefix를 `/v1`로 바꾸고 기존 엔드포인트 경로를 전부 고치기
  - 둘 다 가능하지만 팀 URL 규칙과 맞지 않음

### 어떻게 풀었나

- 팀 규칙에 맞춰 **쿼리 방식**으로 정함 : `GET /v1/reservations?festival_id=1`
  - 기존 예매 라우터 prefix에 그대로 들어가서 라우터를 따로 만들 필요가 없음
  - 예매 라우터에는 아직 `GET ""`가 없어서 기존 API와 겹치지 않음
- 쿼리 파라미터
  - `festival_id` : 필수
  - `day`, `statuses` : 선택 필터
  - `page`, `size` : 페이지네이션
- 라우터 단계에서 주의할 점
  - 리스트를 쿼리로 받으려면 `Query()`를 써야 함 (그냥 `list[...]`로 적으면 FastAPI가 body로 착각함)
  - URL만 보면 일반 사용자도 부를 수 있으니 관리자 검사(403)를 반드시 넣어야 함 → users의 `verify_admin` 사용
- URL이 어떻게 정해지든 서비스 코드는 같아서 서비스 작업부터 진행하기로 함

## 4. 축제 서비스: KST import를 shared로 교체 (#110 리뷰 TODO 해결)

### 막힌 점, 고민

- 공용 시간 유틸(`shared/core/time.py`)을 만들었는데, 축제 서비스는 아직 `from performances.domain.performance import KST`로 가져오고 있었음
- 바로 위에 `# TODO: KST 상수 통일 회의 후 shared로 교체 (#110 리뷰)` 주석이 남아 있었음
  - 이번 PR이 바로 그 TODO를 해결하는 작업이었는데 빠뜨린 것임
- `performance.py`가 이미 공용 KST를 다시 가져오고 있어서 동작은 정상이었음
  - 그래서 "돌아가는데 왜 고쳐야 하지?"라는 의문이 들었음

### 무엇을 어떻게 했나

- KST를 가져오는 경로를 비교해 봄

| 구분          | 수정 전                                           | 수정 후                                     |
| ------------- | ------------------------------------------------- | ------------------------------------------- |
| import        | `from performances.domain.performance import KST` | `from shared.core.time import KST, now_utc` |
| 가져오는 경로 | 축제 서비스 → 공연 도메인 → shared                | 축제 서비스 → shared                        |
| 취소 시각     | `festival.cancel(datetime.now(UTC))`              | `festival.cancel(now_utc())`                |

- TODO 주석을 지움
- 이제 안 쓰는 `UTC`, `datetime` import도 정리함 (`date`만 남김)

### 어떻게 풀었나

- 동작이 같아도 **구조가 문제**였다는 것을 이해함
  - 축제 서비스가 시간대 하나 때문에 공연 도메인 파일에 의존하고 있었음
  - 공연 쪽에서 import를 바꾸거나 지우면 축제 서비스도 같이 깨질 수 있음
- 여러 도메인이 함께 쓰는 값은 다른 도메인을 거치지 말고 shared에서 직접 가져오기로 정리함
- 현재 시각도 `datetime.now(UTC)`를 직접 쓰지 않고 `now_utc()`로 통일해서 다른 서비스와 같은 방식이 됨
- 수정한 뒤 ruff 검사와 전체 테스트(151 passed)로 확인함
