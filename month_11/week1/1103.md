# 4계층(4-Layered) 아키텍처

### 표현 계층 ( Presentation )

- 사용자(클라이언트)의 요청을 받아 응용 계층에 전달, 처리 결과를 응답으로 돌려줌
- 요청 데이터 형식 검증, 응답 데이터 변환(DTO)
- ex: Controller, View

<hr>

### 응용서비스 계층 ( Application )

- 사용자 요청을 처리하기 위한 흐름(유스케이스) 조율
- 비즈니스 규칙을 직접 구현하는 것이 아닌 도메인 객체에 처리 위임
- 트랜잭션 처리, 도메인과 인프라 사이의 연결 담당
- ex: Service

<hr>

### 도메인 계층 ( Domain )

#### 도메인

- 비즈니스 영역의 해결할 문제
- 개발을 통해서 최종적으로 해결해야 하는 비즈니스 영역의 문제
- 도메인 전문가와 소통을 통해서 도메인 지식을 높여야 함

#### 도메인 계층의 역할

- 시스템의 핵심 비즈니스 규칙(도메인 규칙)을 구현
- 외부 기술(DB, 프레임워크 등)에 의존하지 않는 순수한 영역
- ex: Entity, Value Object, 도메인 서비스

#### 도메인 모델링

- 비즈니스 요구사항(도메인 규칙)을 코드로 구체화(설계)하는 과정

#### 애그리거트 ( Aggregate )

- 서로 관련된 도메인 객체들을 하나로 묶은 단위
- 데이터를 변경할 때 이 묶음 전체를 한 덩어리로 취급

##### 왜

- 도메인 모델이 커지면 Entity와 Value Object가 많아지고, 객체간의 관계가 복잡해짐
- 아무 객체나 직접 수정이 가능하면 비즈니스 규칙(일관성)이 쉽게 깨짐
- 그러므로 관련 객체를 묶고, 반드시 정해진 입구를 통해서만 수정하게 만듦

##### EX

```
Order (애그리거트 루트)
 ├─ OrderLine (주문 항목들)
 ├─ ShippingInfo (배송 정보)
 └─ Orderer (주문자)
```

- OrderLine을 직접 수정하는 것이 아닌, order.changeOrderLines(...)처럼 order를 통해야 변경 가능
- `주문 항목이 바뀌면 총 금액도 다시 계산한다` 같은 규칙이 항상 지켜짐

##### 애그리거트 루트 ( Aggregate Root )

- 애그리거트를 대표하는 최상위 Entity
- 애그리거트 안의 객체들의 일관성을 유지하도록 책임을 가짐
- 외부에서는 루트만 참조 가능, 내부 객체에는 직접 접근 불가능
- setter를 열어두지 말고, 의미 있는 도메인 메서드를 제공해야 함
  - ex: setStatus() 대신 cancel()

##### 주요 규칙

| 규칙                                   | 설명                                                        |
| -------------------------------------- | ----------------------------------------------------------- |
| 루트를 통해서만 변경                   | 내부 객체를 직접 수정할 수 없음                             |
| 다른 애그리거트는 ID로 참조            | Member member 대신 MemberId memberId 사용 → 결합도가 낮아짐 |
| 리포지토리는 애그리거트 단위           | OrderRepository는 있지만 OrderLineRepository는 두지 않음    |
| 한 트랜잭션에서는 한 애그리거트만 수정 | 여러 애그리거트를 바꿔야 하면 응용 서비스나 이벤트로 처리   |
| 함께 생성되고 함께 삭제됨              | 라이프사이클이 같은 객체끼리 묶음                           |

##### 4계층과 관계

- 애그리거트는 도메인 계층에 속함
- 응용 계층은 리포지토리로 애그리거트를 가져와서 루트의 메서드를 호출
- 인프라 계층은 애그리거트를 통째로 저장하고 불러옴

### 인프라 계층 ( Infrastructure )

- 외부 시스템과의 연동을 담당하는 기술적인 구현 영역
- DB 접근, 외부 API 호출, 메시징, 파일 처리 등
- ex: Repository 구현체, DB 연결 설정

## 도메인 4계층 아키텍처의 특징

- 역할과 책임을 기준으로 명확히 격리된 4개의 계층 폴더를 두는 아키텍처
- 상위 계층에서 하위 계층으로만 흐르는 단방향 흐름을 가짐
- 핵심 도메인은 외부 환경 변화로부터 안전하게 보호됨

### 전체 흐름

- 전체적인 흐름은 중심 역할 == 응용 계층
- 응용 계층은 데이터베이스 처리를 위해 인프라 계층을 사용
- 가져온 데이터에 핵심 규칙을 적용하기 위해 도메인 계층을 사용
- 응용 계층에서 두 방향으로 의존성이 연결되는 구조를 가짐

```
표현 → 응용 → 인프라
          ↘ 도메인
```

<hr>

### (참고) 의존성 역전(DIP)

- 도메인/응용 계층이 인프라 구현체에 직접 의존하면 DB 등 기술이 바뀔 때 핵심 로직도 영향을 받음
- 그래서 도메인 쪽에 인터페이스(ex: Repository)를 두고, 인프라 계층이 그 인터페이스를 구현하게 함
- 이렇게 하면 핵심 도메인이 외부 기술에 의존하지 않게 됨
- 그래서 실제로는 인프라가 도메인에 의존하게 됨 (의존 방향이 역전됨)

## @dataclass

- 데이터를 담는 클래스를 간단하게 만들어주는 데코레이터
- 필드 선언(`이름: 타입`)을 보고 `__init__`, `__repr__`, `__eq__`를 자동으로 생성
- 타입 힌트가 없는 변수는 필드로 인식하지 않음
- 직접 정의한 메서드는 덮어쓰지 않음

```python
from dataclasses import dataclass

@dataclass
class Money:
    amount: int
    currency: str

m = Money(1000, "KRW")    # __init__
print(m)                  # Money(amount=1000, currency='KRW')  ← __repr__
m == Money(1000, "KRW")   # True  ← __eq__ (값 비교)
```

#### 주요 옵션

| 옵션                          | 의미                                     |
| ----------------------------- | ---------------------------------------- |
| `frozen=True`                 | 불변 객체가 됨 (값을 바꾸면 에러)        |
| `eq=False`                    | 값 비교 대신 객체 동일성으로 비교        |
| `order=True`                  | `<`, `>` 등 비교 연산자 생성             |
| `field(default_factory=list)` | 리스트처럼 바뀔 수 있는 값의 기본값 지정 |

#### 도메인 계층에서 활용

- Value Object → `@dataclass(frozen=True)` : 값이 같으면 같은 객체, 변경 불가
- Entity → `@dataclass(eq=False)` : 필드 값이 아니라 ID로 구분해야 하므로 기본 `__eq__`를 쓰지 않음

## @classmethod

- 인스턴스가 아니라 클래스 자체를 첫 번째 인자(`cls`)로 받는 메서드를 만드는 데코레이터
- 인스턴스 없이 클래스에서 바로 호출 가능
- 주로 팩토리 메서드(대체 생성자)로 사용

```python
class Money:
    def __init__(self, amount: int, currency: str):
        self.amount = amount
        self.currency = currency

    @classmethod
    def won(cls, amount: int):      # cls == Money
        return cls(amount, "KRW")   # Money(amount, "KRW")와 같음

m = Money.won(1000)
```

#### 메서드 종류 비교

| 종류            | 첫 인자           | 접근할 수 있는 것 | 주 용도                       |
| --------------- | ----------------- | ----------------- | ----------------------------- |
| 일반 메서드     | `self` (인스턴스) | 인스턴스 + 클래스 | 객체의 동작                   |
| `@classmethod`  | `cls` (클래스)    | 클래스            | 팩토리 메서드, 대체 생성자    |
| `@staticmethod` | 없음              | 둘 다 없음        | 클래스에 묶어 둔 일반 함수    |

#### cls(...)를 쓰는 이유

- 상속받은 클래스에서 호출하면 `cls`가 그 자식 클래스가 됨
- 그래서 자식 클래스에서 호출해도 자식 객체가 만들어짐

#### 도메인에서 활용

- 애그리거트를 만들 때 생성 규칙을 담은 팩토리 메서드로 사용

```python
@dataclass(eq=False)
class Order:
    id: int
    lines: list[OrderLine]

    @classmethod
    def create(cls, id: int, lines: list[OrderLine]):
        if not lines:
            raise ValueError("주문 항목은 최소 1개 이상")
        return cls(id, lines)
```

- `주문 항목이 없는 주문은 만들 수 없다` 같은 규칙을 생성 단계에서 지킬 수 있음
