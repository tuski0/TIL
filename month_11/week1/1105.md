### **공통 Exception 상태 코드: fastapi.status vs http.HTTPStatus**

#### **막힌 점, 고민**

- 공통 예외(`SharedException`)에서 HTTP 상태 코드를 어떤 방식으로 쓸지 고민함
- 튜터 repo(shared/core/exceptions.py)는 `from fastapi import status`를 사용함
- 그런데 각 도메인 예외(예: `ReservationNotFound`)가 `SharedException`을 상속하면 domain이 간접적으로 FastAPI에 의존하게 됨
- 4계층을 쓰는 이유가 의존성을 낮추기 위해서인데, 튜터 방식을 따르는 게 맞는지 고민됨

#### **무엇을 어떻게 했나**

- 두 방식을 비교함

| **구분**      | **fastapi.status**                     | **http.HTTPStatus**                      |
| ------------- | -------------------------------------- | ---------------------------------------- |
| 출처          | FastAPI(실제로는 Starlette)            | 파이썬 표준 라이브러리                   |
| 값            | 정수 상수 (`HTTP_404_NOT_FOUND = 404`) | IntEnum (`HTTPStatus.NOT_FOUND`, 값 404) |
| 응답에 쓸 때  | 그대로 사용                            | 그대로 사용 (int의 하위 타입)            |
| 추가 기능     | 없음                                   | `.phrase`(“Not Found”) 같은 설명         |
| domain 의존성 | domain이 FastAPI에 의존하게 됨         | 의존성 없음                              |

- import가 이어지는 구조를 확인함
  - reservations/domain/exceptions.py → `shared.core.exceptions` → `fastapi`
  - Enum을 models.py에서 domain으로 옮긴 것과 같은 문제임
- 동작 차이는 없다는 것을 확인함
  - `HTTPStatus.NOT_FOUND == 404`는 True
  - `JSONResponse(status_code=...)`에 그대로 넣을 수 있음
- 422 이름 변경도 알게 됨
  - 최신 HTTP 표준에서 422의 이름이 “Unprocessable Content”로 바뀜
  - Python 3.13 `HTTPStatus`에는 `UNPROCESSABLE_CONTENT`와 기존 이름 `UNPROCESSABLE_ENTITY`가 둘 다 있음 (값은 같은 422)

#### **각 방식의 장점**

- **튜터 방식(fastapi.status)**
  - 팀원들이 튜터 repo를 보면서 작업하므로 비교하고 따라 하기 쉬움
  - 튜터에게 질문하거나 리뷰받을 때 편함
  - `shared/core`는 모든 계층이 같이 쓰는 공통 영역이라 FastAPI 의존을 허용한다고 볼 수도 있음 (튜터 `ser.py`도 `shared.core.exceptions`를 import함)
- **HTTPStatus 방식**
  - “domain은 FastAPI·SQLAlchemy를 import하지 않는다”는 규칙을 끝까지 지킬 수 있음
  - Enum 이동, domain 완료 조건 등 지금까지 세운 기준과 일관됨

#### **판단 기준**

- 프로젝트 목적이 **튜터 구조를 배우고 맞추는 것**이면 → fastapi.status
- 목적이 **4계층 의존성 규칙을 엄격하게 지키는 것**이면 → HTTPStatus
- 어느 쪽이든 코드 차이는 import 한 줄과 상수 이름 정도라 나중에 바꾸기 쉬움

#### **어떻게 풀었나 (진행 중)**

- 바로 결정하지 않고 팀 합의 안건으로 올리기로 함
- 튜터에게 “domain 예외가 `shared.core.exceptions`를 상속하면 FastAPI에 의존하게 되는데 의도하신 건지” 확인할 예정
- 초안은 먼저 만들어두고, 합의 결과에 따라 import와 상수 이름만 교체
- 결정되면 이슈 #27의 결정 사항과 완료 조건도 함께 수정

## Repository 통일 논의

도메인마다 repository를 각자 만들다보니 메서드 이름과 목록 조회 방식이 다름

다음 단계인 구현체와 service를 구현하기 전에 규칙을 맞추면, 서로 코드를 볼 때 덜 헷갈리고 리뷰가 쉬워질것 같음

### 안건 1. 메서드 이름: `find_*`로 통일

**현재**

- 예매(#49), 축제(#64): `find_by_id`, `find_by_user_id`
- 티켓(#67): `get_by_code`, `get_by_id_for_user`

**제안**: 조회는 전부 `find_*`

| 하는 일   | 이름                    |
| --------- | ----------------------- |
| 조회      | `find_by_*`, `find_all` |
| 개수      | `count`, `count_by_*`   |
| 존재 여부 | `exists_*`              |
| 저장      | `save`                  |

**이유**: 이미 머지된 예매와 튜터 repo가 `find_*`라서 티켓만 바꾸면 끝나요.

**정할 것**: 이 규칙으로 확정할지

### 안건 2. 생성/수정: `save` 하나 vs `add` + `save`

**현재**

- 예매, 축제, 튜터: `save` 하나 (id가 None이면 생성, 있으면 수정)
- 티켓: `add`(생성)와 `save`(수정)를 분리

**설명**

- `save` 하나: 다른 도메인, 튜터와 같음
- 분리: 생성인지 수정인지 이름만 보고 알 수 있음

**정할 것**: 어느 쪽으로 통일할지

### 안건 3. 목록 조회: 페이지를 어떻게 나눌지

**현재**

- 축제(#64): `find_all(offset, limit)` + `count()` → 메서드 2개 (튜터와 같음)
- 티켓(#67): `list_by_user(page, size)` → `(목록, 개수)`를 한 번에 반환

**제안**: 튜터 방식으로 통일

```
repository: find_...(조건, offset, limit) + count_...(조건)
service   : offset = (page - 1) * size 계산 → PageResponse로 묶기
```

**이유**

- repository는 "몇 개 건너뛰고 몇 개 가져와"만 알면 돼요. page라는 화면 개념은 service가 담당해요.
- 튜터, 축제와 같은 모양이라 따라 하기 쉬워요.

**단점도 공유**: 목록과 개수에 같은 조건을 두 번 넘겨야 해요. service에서 두 메서드를 나란히 호출하면 실수를 막을 수 있어요.

**페이지가 필요 없는 경우**: 데이터가 적으면 전부 가져와도 돼요. 예: 내 예매 목록(1인 최대 4장)

**정할 것**: 튜터 방식으로 통일할지, 티켓 방식으로 할지

### 안건 4. commit은 누가 하나

**현재**: 축제, 티켓 모두 “repository는 commit 안 함, service가 함”으로 적혀 있음

**제안**: 이대로 확정

**이유**: 예매하면서 티켓도 만드는 것처럼 여러 저장을 한 번에 성공/실패시켜야 할 때, service에서 마지막에 한 번 commit해야 중간에 반만 저장되는 일이 없어요.

#### **양일권(BOTH)을 예매에 어떻게 표현할지: performance_id → festival_id**

#### **막힌 점, 고민**

- 예매(`reservations`)는 회차 하나(`performance_id`)를 가리키게 설계돼 있었음
- 그런데 양일권은 예매 1건이 토·일 두 회차를 포함해서 `performance_id` 하나로는 표현이 안 됨
- 날짜별 구매 한도도 같이 고려해야 했음
  - 사용자 1명은 날짜별 최대 2장
  - 양일권 1장은 토 1장 + 일 1장으로 계산
  - 그래서 토요일권을 먼저 사면 양일권을 살 수 있는 수량이 줄어듦
- 조건이 많아서 어디부터 손대야 할지 막막했음

#### **무엇을 어떻게 했나**

- 가능한 방법을 비교함

| **구분**      | **performance_id 2개 / 중간 테이블** | **reservations.festival_id로 변경**                |
| ------------- | ------------------------------------ | -------------------------------------------------- |
| 바뀌는 테이블 | reservations + 새 테이블             | reservations만                                     |
| 회차 찾는 법  | 저장된 id를 그대로 사용              | `festival_id` + `ticket_type`으로 조회             |
| 날짜별 정보   | 예매가 가짐                          | 티켓이 가짐 (tickets에 이미 `performance_id` 있음) |
| 부분 취소     | 가능하게 만들 수 있음                | 불가 (전체 취소만)                                 |

- 결제한 예매는 전체 취소만 하기로 해서 부분 취소가 필요 없었음. 그래서 festival_id 방식을 선택함
- 회차 요일은 `starts_at`을 한국 시간으로 바꿔서 계산함 (`weekday()` 5 = 토, 6 = 일). performances에 요일 컬럼을 추가하지 않아도 됨
- 잔여석은 찾은 회차를 전부 차감하고, 하나라도 부족하면 전체를 실패시킴

```
UPDATE performances SET remaining_count = remaining_count - :q
WHERE id = :id AND remaining_count >= :q
```

- 티켓은 날짜(회차)별로 발급함. 양일권 1장이면 토·일 티켓 2장이 발급됨
- 날짜별 한도를 어디서 판단할지 정함
  - 기존 예매 조회는 application(service)이 맡음
  - 조회 결과를 합산하고 판단하는 일은 domain/service.py가 맡음
  - 여러 예매를 함께 봐야 하는 규칙이라 엔티티 하나에 넣기 어려움
- 확인할 경우를 정리함

| **기존 예매** | **새 요청** | **결과**      |
| ------------- | ----------- | ------------- |
| 없음          | 양일권 2    | 성공          |
| 토요일권 1    | 양일권 2    | 실패 (토 3장) |
| 토요일권 1    | 양일권 1    | 성공          |
| 양일권 1      | 일요일권 1  | 성공          |
| 양일권 2      | 토요일권 1  | 실패 (토 3장) |

- `CANCELED`, `EXPIRED` 예매는 합산에서 제외함

- 409/422는 공통 예외 기준으로 나눔: "다른 시점에 보냈으면 성공했을까?"

#### **전역 예외 처리: HTTPException이 공통 응답 형식을 벗어나는 문제**

#### **막힌 점, 고민**

- PR 리뷰에서 지적을 받음
  - `HTTPException`은 `SharedException`이 아니라서 FastAPI 기본 핸들러가 먼저 잡음
  - 그래서 `Exception` 핸들러까지 오지 않음
- 그 결과 404나 `raise HTTPException`의 응답이 `{"detail": ...}`로 나가서, 프론트와 약속한 `APIResponse` 형식이 깨짐
- Starlette가 뭔지 몰랐음. FastAPI 하나로 공통 처리하려고 그냥 `HTTPException`을 썼었음
- 도메인 예외를 `SharedException` 상속으로 다 만들면 이 핸들러가 필요 없지 않나 하는 의문이 들었음

#### **무엇을 어떻게 했나**

- Starlette의 역할을 정리함
  - FastAPI의 뼈대 프레임워크임. `fastapi`를 설치하면 같이 설치됨
  - 라우팅, 미들웨어, 예외 처리는 Starlette가 맡음
  - Pydantic 검증, `Depends`, Swagger는 FastAPI가 그 위에 얹은 것임
- 예외가 처리되는 층 구조를 확인함

| **층**                       | **붙는 핸들러**                                                                        |
| ---------------------------- | -------------------------------------------------------------------------------------- |
| ServerErrorMiddleware (바깥) | `Exception` (500)                                                                      |
| ExceptionMiddleware (안쪽)   | `SharedException`, `RequestValidationError`, `HTTPException` (기본 핸들러가 여기 있음) |
| Router                       | 맞는 URL이 없으면 `HTTPException(404)` 발생                                            |

- 없는 URL이면 안쪽 기본 핸들러가 응답하고 끝나서, 바깥 `Exception` 핸들러까지 올라가지 않음
- 두 404의 차이를 비교함

| **구분**  | **NotFoundException (SharedException)** | **Starlette 404**          |
| --------- | --------------------------------------- | -------------------------- |
| 뜻        | 주소는 맞는데 데이터가 없음             | 그런 API 자체가 없음       |
| 발생 위치 | 우리 service 코드                       | 라우터 (우리 코드 실행 전) |
| code      | 도메인 코드                             | `HTTP_ERROR`               |

- 도메인 예외로 막을 수 없는 경우를 정리함
  - 없는 URL(404)
  - 허용하지 않는 메서드(405)
  - 토큰 누락(`HTTPBearer`, 401)
- 튜터 repo를 확인함
  - 모든 브랜치에 이 핸들러가 없음
  - `HTTPBearer(auto_error=True)`를 쓰는 곳에서 같은 문제가 생김
- 핸들러를 등록할 때 주의할 점을 확인함
  - `fastapi.HTTPException`은 Starlette `HTTPException`의 자식 클래스임. 부모(Starlette) 클래스로 등록해야 둘 다 잡힘
  - 401 응답의 `WWW-Authenticate` 헤더를 유지하려면 `headers=exc.headers`를 넘겨야 함
  - 로그 레벨은 4xx는 `warning`, 예상하지 못한 500은 `exception`으로 나눔

#### **어떻게 풀었나**

- shared/core/exception_handlers.py에 Starlette `HTTPException` 핸들러를 추가함 (핸들러가 4종이 됨)
- 초안의 `error=None` 오타를 `errors=None`으로 고침. 그대로 뒀으면 TypeError가 나서 500이 됐을 것임
- TestClient는 httpx가 없어서 쓸 수 없었음. 대신 ASGI로 앱을 직접 호출해서 검증함
  - 404, 405, 401은 `HTTP_ERROR` 형식으로 응답됨
  - 401 응답에는 `WWW-Authenticate: Bearer` 헤더가 유지됨
  - `NotFoundException`은 기존대로 `NOT_FOUND`로 응답됨
- 이슈 #76과 PR mjlee0914/BE-project-teamD#77 · fix: 전역 예외 핸들러에 HTTPException…을 생성함. 리뷰 승인을 기다리는 중임
- 노션에 팀 공유 문서를 작성함
- 팀 규칙을 제안함
  - 에러는 `SharedException`을 상속한 예외로만 발생시킴
  - 코드에서 `raise HTTPException`을 직접 쓰지 않음
  - 이 핸들러는 프레임워크가 내는 예외를 받는 안전망으로만 둠
