#### **예매 저장소: ORM 모델 ↔ 엔티티 변환 (`_to_entity` / `_to_model`)**

#### **막힌 점, 고민**

- 튜터 repo는 `mappers.py` 파일을 따로 만들어 `BoardMapper`로 변환하는데, 우리는 이 파일이 없어서 변환 코드를 어디에 둬야 할지 헷갈렸음
- ORM 모델과 엔티티가 각각 무엇이고 왜 변환해야 하는지 정확히 몰랐음
- `_to_entity`처럼 앞에 `_`를 붙이는 이유가 궁금했음

#### **무엇을 어떻게 했나**

- 두 객체의 역할을 구분함

| **구분** | **ORM 모델** (infrastructure/models.py)    | **엔티티** (domain/entity.py)             |
| -------- | ------------------------------------------ | ----------------------------------------- |
| 정체     | DB 테이블과 1:1로 매핑된 SQLAlchemy 클래스 | 순수 파이썬 클래스                        |
| 역할     | DB 저장·조회                               | 비즈니스 규칙 (`cancel()`, `create()` 등) |
| 의존성   | SQLAlchemy에 의존함                        | 외부 라이브러리 없음                      |

- 변환이 필요한 이유를 정리함
  - 저장소가 ORM 모델을 그대로 돌려주면 application과 domain이 SQLAlchemy에 의존하게 됨
  - 그래서 저장소 경계에서 엔티티로 바꿔서 돌려줌
- mappers.py를 따로 만들지 않고 `SqlalchemyReservationRepository` 클래스 안에 `@staticmethod`로 둠
  - `_to_entity(model)`: ORM 모델 → `Reservation` 엔티티 (16개 필드)
  - `_to_model(entity)`: 엔티티 → `ReservationModel`
  - 호출은 `self._to_entity(...)`로 함
- 이름 충돌을 피하려고 ORM 모델은 별칭으로 import함
  - `from reservations.infrastructure.models import Reservation as ReservationModel`

#### **어떻게 풀었나**

- `_` 접두사는 클래스 내부에서만 쓰는 함수라는 관례 표시임 (외부에서 호출하지 말라는 뜻)
- 튜터의 mappers.py는 변환 코드를 파일로 분리한 것뿐이고, 하는 일은 같다는 것을 이해함
- 처음에는 이런 실수를 했었음
  - `return model(...)`처럼 엔티티 대신 모델 객체를 만듦
  - 필드 누락
  - 오타 (`statis`)
- 실수를 고친 뒤 실제 DB로 저장 → 조회 결과가 같은 값인지 확인함

#### **예매 저장소: `save()`의 신규 저장과 수정 구분**

#### **막힌 점, 고민**

- `save()` 하나로 신규 등록과 수정을 둘 다 처리해야 하는데 구분하는 방법을 몰랐음
- 수정할 때 모든 필드를 덮어써야 하는지, None이나 기본값이 있는 필드도 다 넣어야 하는지 고민했음

#### **무엇을 어떻게 했나**

- `reservation.id` 유무로 분기함
  - id가 있으면 수정: `session.get()`으로 기존 행을 가져와 바뀐 필드만 덮어씀
  - id가 없으면 신규: `_to_model()`로 변환 → `add` → `flush` → `refresh`
- 예매에서 바뀌는 값이 무엇인지 정리함
  - 이름·장소·가격·수량 등은 생성할 때 정해지고 바뀌지 않음
  - 바뀌는 건 상태 관련 값뿐임: `status`, `confirmed_at`, `canceled_at`
  - 그래서 수정할 때는 이 3개만 덮어씀
- 세션 메서드 역할을 정리함

| **메서드**               | **역할**                                     |
| ------------------------ | -------------------------------------------- |
| `session.get(Model, id)` | 기본키로 1건 조회                            |
| `add()`                  | 세션에 새 객체 등록                          |
| `flush()`                | SQL을 DB에 보냄 (commit은 아님, id가 생성됨) |
| `refresh()`              | DB 값을 객체에 다시 읽어옴                   |
| `scalars(stmt).all()`    | 조회 결과를 모델 리스트로 받음               |

- commit은 저장소가 아니라 application(유스케이스)에서 함

#### **어떻게 풀었나**

- 이런 실수를 고침
  - 값 뒤에 쉼표가 붙어 tuple이 됨
  - 매개변수 이름을 `Reservation`으로 해서 클래스 이름을 가림
  - `to_entity`에 `_`를 빠뜨림
- 처음에는 id 체크 없이 `session.get()`을 호출해서 “fully NULL primary key” SAWarning이 났음
  - `if reservation.id is not None:`으로 먼저 분기해서 해결함
- 실제 Postgres로 검증함
  - 신규 저장하면 id 1이 생성됨
  - `cancel()` 후 save하면 상태만 바뀌고 나머지 필드는 유지됨
  - `find_by_user_id`는 2건 조회, 없는 사용자는 `[]`, 없는 id는 `None`이 나옴

#### **application 서비스: 다른 도메인(축제) 정보를 가져오는 방법**

#### **막힌 점, 고민**

- 예매 생성(`create`)에는 축제 이름·장소를 스냅샷으로 저장해야 하는데, 이 값은 festivals 도메인에 있음
- reservations/application/service.py에서 `FestivalRepository`를 직접 import하면 예매가 축제 도메인에 의존하게 됨
- 4계층 규칙(application → domain)은 지키지만 도메인끼리 의존이 생기는 게 맞는지 고민했음

#### **무엇을 어떻게 했나**

- 두 방법을 비교함

| **구분**              | **방법 1: 직접 import** | **방법 2: `FestivalReader` 인터페이스**    |
| --------------------- | ----------------------- | ------------------------------------------ |
| 축제 의존             | application이 의존함    | infrastructure의 Impl만 의존함             |
| 만들 것               | 거의 없음               | `FestivalSnapshot`, `FestivalReader`, Impl |
| 축제 저장소가 없을 때 | 실행·테스트 불가        | Impl에서 직접 조회해서 진행 가능           |
| 축제 쪽이 바뀔 때     | 예매 service 수정       | Impl만 수정                                |
| 테스트                | 실제 축제 저장소 필요   | 가짜 Reader로 대체 가능                    |

- 튜터 repo(`auth_ex` 브랜치)가 어떻게 했는지 확인함
  - auth/domain/service.py: `UserCredentialVerifier(ABC)`. 약속만 정하고 user를 import하지 않음
  - auth/application/service.py: `AuthService`가 추상 타입만 받음
  - auth/infrastructure/credentials_verifier.py: `UserCredentialVerifierImpl`. **여기서만** `UserRepository`를 import함
  - wiring/auth.py: Impl을 만들어 `AuthService`에 주입함
- 즉 튜터도 application에서 다른 도메인을 직접 import하지 않음

#### **각 방식의 장점**

- **방법 1**
  - 파일이 늘지 않고 구조가 단순함
  - 축제 저장소가 곧 나온다면 가장 빠름
- **방법 2**
  - 예매의 domain과 application은 축제를 모름
  - 축제 저장소 구현체(mjlee0914 담당)가 없어도 지금 진행할 수 있음
  - 테스트할 때 축제 DB 없이 가짜 Reader로 검증 가능
  - 튜터 구조와 같음

#### **어떻게 풀었나 (진행 중)**

- 방법 2로 진행하는 방향으로 기울었음
  1. domain/repository.py에 `FestivalSnapshot`(dataclass)과 `FestivalReader`(ABC) 추가
  2. application/service.py의 생성자는 `ReservationRepository`와 `FestivalReader`만 받음
  3. `infrastructure`의 Impl에서 축제 테이블을 조회해 `FestivalSnapshot`으로 반환
- 작은 프로젝트에서는 방법 1도 틀린 건 아니라서 팀 회의에서 최종 확인할 예정

#### **import와 타입 힌트**

#### **막힌 점, 고민**

- 다른 도메인 import를 피하려고 인터페이스를 만드는데, 결국 application에서 그 인터페이스를 또 import해야 해서 왜 필요한지 헷갈렸음
- "어차피 import할 거면 그냥 축제 저장소를 쓰면 되지 않나" 하는 의문이 들었음

#### **무엇을 어떻게 했나**

- application에서 `FestivalReader`를 import하는 이유를 정리함
  - **타입 힌트용임.** 파이썬은 덕 타이핑이라 타입을 빼도 `find_by_id`만 있으면 실행은 됨
  - 그래도 넣는 이유
    - 이 자리에 어떤 약속(메서드)을 지키는 객체가 와야 하는지 코드에 드러남
    - 에디터 자동완성이 됨
    - ruff, 타입 검사, 리뷰에서 실수를 잡을 수 있음
- 같은 import라도 무엇을 import하느냐가 다르다는 점을 구분함

| **import 대상**                                  | **위치**    | **의존 문제** |
| ------------------------------------------------ | ----------- | ------------- |
| `reservations.domain.repository.FestivalReader`  | 자기 도메인 | 없음          |
| `festivals.domain.repository.FestivalRepository` | 다른 도메인 | 있음          |

#### **어떻게 풀었나**

- 규칙으로 정리함
  - domain과 application은 **자기 도메인 것만** import함
  - 다른 도메인 import는 **infrastructure의 구현체에서만** 함
  - 연결은 wiring에서 함
- 튜터 auth 코드도 같은 규칙을 따른다는 것을 확인함
