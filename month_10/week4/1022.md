# 개인 개발 일지

## **막힌 점**

기존에는 대카테고리를 선택하면 하나의 박스 안에 선택한 대카테고리와 소카테고리가 표시되었다.

이를 두 개의 박스로 나누면서, 상단에는 대카테고리 목록을 항상 유지하고 하단에는 선택한 대카테고리에 속한 소카테고리만 표시해야 했다.

## **어떻게 풀었나**

- 조회한 `categories`에서 `parent_id`가 `null`인 항목을 대카테고리로 분류해 상단 박스에 표시했다.
- 선택한 대카테고리의 `id`와 `parent_id`가 일치하는 항목을 찾아 하단 박스에 표시했다.

```
const topCategories = categories.filter(
    (category) => category.parent_id === null,
);

const subCategories = categories.filter(
    (category) => category.parent_id === selectedTopCategoryId,
);
```

- 소카테고리를 선택해도 해당 항목의 `parent_id`로 대카테고리를 찾도록 하여 상단 선택 표시와 하단 목록을 유지했다.
- `ALL PRODUCTS`를 선택하면 하단 박스가 표시되지 않도록 조건부 렌더링했다.

실제 구현에서는 Supabase에서 카테고리를 조회한 뒤, **브라우저에서 `filter()`로 목록을 나누어 처리**했다.

# 2. 정렬 기능 구현

## **막힌 점**

정렬 드롭다운에서 항목을 선택했을 때, 선택한 기준에 따라 상품의 표시 순서가 변경되어야 했다.

또한 카테고리를 변경해도 정렬 기준을 유지하고, `Default`를 선택하면 기존 상품 순서로 돌아가야 했다.

## **어떻게 풀었나**

1. `useState`로 현재 선택한 정렬 기준을 관리했다.

```
const [sortOrder, setSortOrder] =
    useState<ProductSortOrder>('default');
```

`sortOrder`에는 현재 기준이 저장된다. 처음에는 `'default'`이고, 낮은 가격순을 선택하면 `'price-low'`로 바뀐다.

1. 드롭다운에서 선택한 값을 `setSortOrder`에 전달하도록 연결했다.

```
<ProductSort
    value={sortOrder}
    onValueChange={setSortOrder}
/>
```

`value`는 드롭다운에 현재 선택값을 전달하고, `onValueChange`는 사용자가 다른 항목을 선택했을 때 부모의 상태를 변경한다.

1. 카테고리로 걸러진 상품을 선택한 기준에 따라 정렬했다.

```
const sortedProducts = sortProducts(
    visibleProducts,
    sortOrder,
);
```

예를 들어 `OUTER`와 낮은 가격순을 선택했다면, **OUTER에 속한 상품만 남긴 뒤 판매가가 낮은 순서로 정렬**한다.

1. 원본 상품 배열을 복사한 뒤 `sort()`로 순서를 변경했다.

```
return [...products].sort((a, b) => {
    if (order === 'price-low')
        return a.salePrice - b.salePrice;

    if (order === 'price-high')
        return b.salePrice - a.salePrice;

    return (
        Date.parse(b.createdAt) - Date.parse(a.createdAt)
        || b.id - a.id
    );
});
```

- 낮은 가격순: 판매가 오름차순
- 높은 가격순: 판매가 내림차순
- 신상품순: 등록일 내림차순, 등록일이 같으면 ID 내림차순
- 기본순: 정렬하지 않고 기존 조회 순서 사용

`[...products]`로 복사하는 이유는 `sort()`가 배열 자체의 순서를 바꾸기 때문이다. 원본을 보존해야 `Default`를 선택했을 때 원래 순서를 다시 사용할 수 있다.

## 막힌 점

1. **토스 테스트 결제와 Supabase 저장**

   결제 금액과 상품 정보를 브라우저 값에 의존하면 안 됐고, 실제 결제 승인 전후의 주문 저장 순서도 고려해야 했습니다. 또 Supabase 서버 전용 키가 프로젝트 루트의 `.env.local`에서 확인되지 않아 실제 결제 승인부터 DB 저장까지는 검증하지 못했습니다.

2. **상품 옵션과 장바구니 데이터**

   Supabase의 상품 옵션 테이블이 비어 있었고, 기존 장바구니의 상품·가격 데이터가 DB 상품과 일치하지 않았습니다.

3. **마이페이지 주문 조회**

   로그인 사용자만 자기 주문을 볼 수 있도록 인증과 주문 조회를 연결해야 했습니다.

## 어떻게 풀었는지

1. **결제 저장**

   주문 금액은 DB의 상품 가격을 기준으로 서버에서 계산하도록 구성했습니다. 결제 준비, 결제 승인 상태 반영, 주문 내역 저장을 Supabase 서버 측 흐름으로 연결하고, 결제 승인 전 재고가 차감되지 않도록 했습니다. 테스트용 설정 방법도 문서에 적었습니다.

   다만 `.env.local`에서 `SUPABASE_SECRET_KEY`를 확인하지 못해 **Toss 승인부터 Supabase 저장까지 실제 연결 테스트는 남아 있습니다.**

2. **상품 옵션과 가격**

   기존 상품 중 일부를 테스트 결제에 사용할 수 있도록 데모 옵션 데이터를 준비했습니다. 결제 금액은 클라이언트의 장바구니 값이 아니라 DB에 등록된 가격을 사용하도록 했습니다.

3. **마이페이**

   로그인 상태와 주문 조회를 연결하고, 마이페이지에서 주문 내역과 상태를 확인할 수 있도록 구성했습니다. 주문 내역은 로그인한 사용자의 데이터만 조회하도록 처리했습니다.
